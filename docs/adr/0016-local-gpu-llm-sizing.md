# ADR-0016. LLM은 로컬 GPU에서 돌린다 — 4비트 양자화 7~14B

**상태**: 채택 (2026-09-06)

`99-open-questions.md` Q4를 확정한다.

## 맥락

ADR-0007은 온프렘 + 모델 어댑터 계층을 확정했으나 **구체적 사양이 미정**이었다.
가용 GPU가 정해져야 모델 크기와 지연 예산이 나온다. ADR-0012(전술망)로 DIL 제약이
붙으면서 온프렘은 선택이 아니라 필수가 됐다.

과제 책임자가 **현재 워크스테이션에서 구동**하는 것으로 확정했다.

## 실측 사양

| 항목 | 값 |
|---|---|
| GPU | NVIDIA GeForce RTX 2080 Ti, **VRAM 11,264 MiB (11 GB)**, compute capability **7.5 (Turing)** |
| 드라이버 | 591.86 |
| CPU | Intel Xeon W-2123 @ 3.60GHz, **4코어 / 8스레드** |
| RAM | 63.7 GB |
| 장비 | Dell Precision 5820 Tower |

> `Win32_VideoController.AdapterRAM`은 **4GB로 잘못 보고한다**(32비트 오버플로).
> 실제 VRAM은 `nvidia-smi` 또는 레지스트리 `HardwareInformation.qwMemorySize`로 확인한다.
> 이 값을 그대로 믿고 모델 크기를 정하면 안 된다.

## 결정

### 1. 모델 크기: 4비트 양자화 기준 7~14B, 상한 14B

11GB VRAM에서 KV 캐시까지 감안한 현실 범위다.

| 크기 | 4비트 가중치 | 판정 |
|---|---|---|
| 7~8B | 약 5~6 GB | **권장.** 컨텍스트 여유 충분 |
| 12~14B | 약 8~9 GB | 가능. 컨텍스트 길이를 줄여야 함 |
| 20B+ | 12 GB 초과 | CPU 오프로딩 필요 → **4코어 Xeon에서는 실용 속도가 안 나온다** |

**14B를 상한으로 둔다.** 32B급은 4비트로도 약 19GB라 들어가지 않고, 부분 오프로딩은
이 CPU에서 대안이 못 된다.

RAM 63.7GB로 CPU 추론은 가능하지만 초당 몇 토큰 수준이라 **데모에 쓸 수 없다.**

### 2. 런타임: GGUF + llama.cpp 계열 (Ollama 등)

Turing(sm_75) 제약을 감안한 선택이다.

- Turing은 bfloat16을 네이티브 지원하지 않고, FlashAttention-2 등 최신 커널 상당수가
  Ampere 이상을 요구한다. **최신 서빙 스택을 그대로 얹으면 막힌다.**
- llama.cpp 계열은 Turing에서 안정적으로 동작하며 Windows 네이티브 지원이 있다.
- 추론만 할 것이므로 CUDA Toolkit 설치는 불필요하다(현재 미설치).

vLLM 등은 Windows에서 WSL2를 거쳐야 하고 Turing 지원도 제약이 있다. 필요해지면 그때 본다.

### 3. 어댑터 계층은 그대로 유지한다 (ADR-0007)

로컬 모델을 직접 호출하지 않고 어댑터 뒤에 둔다. 개발 중 API 모델로 대조하거나
나중에 엣지 하드웨어로 옮길 때 호출부를 고치지 않기 위해서다.

### 4. 이 사양이 아키텍처를 강제한다

**11GB GPU로는 경보마다 LLM을 호출하는 트리아지가 불가능하다.** LANL만 해도 인증
이벤트가 10.5억 건이다. 경보당 수 초의 지연이면 산술적으로 성립하지 않는다.

즉 ADR-0003(상태 산출은 결정론 계층 전담, LLM은 설명 전담)은 **원칙이자 이 하드웨어에서
강제되는 결론**이다. 논문에서 이 점을 그대로 쓸 수 있다 — 설계 선택이 자원 제약과
독립적으로 옳았음을 보이는 대신, 두 근거가 같은 답을 가리킨다고 쓰는 편이 정직하다.

LLM의 호출 빈도는 **사건 단위**(브리핑 생성, 자연어 질의 응답)이지 이벤트 단위가 아니다.
이 빈도에서는 11GB로 충분하다.

## 근거

- 데모(ADR-0014)에서 브리핑 한 단락 생성은 8B 4비트 기준 수 초 안에 끝난다.
  경보 트리아지와 달리 사람이 기다릴 수 있는 시간이다.
- 전술망 DIL 제약(ADR-0012 6항)상 클라우드 API는 배포 형상에서 가정할 수 없다.
  개발 편의를 위해 클라우드를 쓰더라도 **평가는 로컬에서 돌아가는 모델로** 해야
  배포 가능성이 담보된다.
- Google Colab Pro도 검토했으나 배포 형상과 어긋난다(대안 절).

## 결과

- Ollama 또는 llama.cpp 설치가 필요하다(현재 둘 다 미설치).
- 모델 후보를 7~8B와 12~14B 두 급으로 좁혀 비교한다. 평가 지표는 `04-evaluation.md`의
  LLM 계층 지표군(사실 정확성, 근거 인용률, ECE/Brier, 프롬프트 인젝션 저항)을 쓴다.
- **데모 경로에 네트워크 의존을 넣지 않는다.** 시연 중 외부 API 호출이 실패하면
  복구할 방법이 없다.
- 컨텍스트 길이 예산을 모델 선정 기준에 넣는다. 11GB에서 14B를 쓰면 컨텍스트가 줄어드는데,
  RAG로 근거 스팬을 넣어야 하므로(ADR-0006, ADR-0009) 컨텍스트가 곧 기능이다.
  **7~8B + 긴 컨텍스트**가 **14B + 짧은 컨텍스트**보다 이 과제에 유리할 수 있다.
  이것을 실측으로 정한다.

## 대안

- **Google Colab Pro**: 기각. 세션이 끊기고 임시 디스크이며, 무엇보다 **전술망 배포
  형상과 정반대**다(클라우드·상시 연결 전제). 개발 중 대형 모델 대조군을 돌리는
  용도로는 유용하므로 완전히 배제하지는 않되, **평가와 데모 경로에는 넣지 않는다.**
- **API 모델(클라우드)을 주 모델로**: 기각. ADR-0007, ADR-0012와 충돌.
- **32B급을 CPU 오프로딩으로**: 기각. 4코어 Xeon에서 실용 속도가 나오지 않는다.

## 재검토 조건

- GPU가 교체되거나 추가되는 경우 — VRAM이 24GB 이상이면 상한이 32B급으로 올라간다.
- 실측 결과 7~14B가 브리핑 품질 요구(ADR-0009 근거 인용률)를 못 맞추는 경우.
  그때는 모델 크기가 아니라 RAG 구성과 프롬프트를 먼저 손본다.
