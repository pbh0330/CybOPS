# ADR-0020. 필수 의존(hard)은 대체되지 않는다

**상태**: 채택 (2026-09-07)

## 맥락

전파 함수 비교(E2, `docs/15-propagation-functions.md`)가 `weighted`의 결함을 제기했다.
tacnet-01 t=300 에서 필수도 1.0인 `S-C2MSG`가 100% 상실인데 작업 저하도는
`(1.0x1.0 + 0.9x0)/1.9 = 52.6%`로 나온다. 음성망이 살아 있다는 이유로 희석된다.

여기에는 어휘 문제가 겹쳐 있었다. `03-mission-ontology.md` 3절이 `requires.w`를
**"필수도"**라고 부르는데 엔진은 그것을 가중 평균의 **상대 가중치**로 썼다. 이름과
계산이 어긋나 있었다.

## 결정

**`requires`에 `hard` 를 추가하고, 필수 의존이 상실되면 작업도 상실된다.**

```json
{"from": "T-CTRL", "to": "S-C2MSG", "w": 1.0, "hard": true}
```

```
task_degradation = max( combine(모든 requires, method),
                        max(hard 인 requires 의 서비스 저하도) )
```

- `hard` 가 없으면 기본 false 다. 가중 평균만 적용된다.
- **`w = 1.0` 인 요구는 `hard` 로 명시한다.** 필수도 1.0 은 "이것 없이는 안 된다"는
  뜻이고, 계산이 그 말을 따르게 한다. 이름과 계산의 불일치를 계산 쪽에서 해소했다.
- `hard` 는 `w` 와 독립이다. 가중치는 여전히 평균 항에 쓰인다.
- 전파 함수는 바꾸지 않는다. 기본값은 `weighted` 그대로다(E2 결론 유지).

### 이 결정으로 바뀌는 숫자

| | 이전 | 이후 |
|---|---|---|
| tacnet t=300 M-C2 | 52.63% | **100.0%** |
| tacnet t=300 상호작용 | 52.63% | **100.0%** |
| defnet DC01+DC02 M-C2 | 80.48% | **84.4%** |
| defnet DC01 단독 | 0% | **0%** (불변) |

**이중화는 그대로 작동한다.** DC01 단독 침해가 여전히 0% 인 것이 그 증거다. hard 는
서비스가 실제로 상실됐을 때만 발동하고, 이중화가 살아 있으면 서비스는 상실되지 않는다.

## 근거

- 필수도 1.0 인 요구가 상실됐는데 임무가 절반만 붉은 화면은 지휘관에게 잘못된 그림을
  준다. 이 과제의 주장은 "경보 콘솔이 못 보는 것을 임무 좌표계가 보여준다"인데,
  임무가 불가능해진 상황을 52% 로 보고하면 그 주장 자체가 약해진다.
- 상호작용 분해가 더 선명해진다. t=300 에서 공격 단독 0%, 환경 단독 0%, 실제 100% 다.
  **어느 원인 하나만으로는 아무 일도 일어나지 않는데 둘이 겹치자 임무가 정지한다.**
  이것이 이 과제의 핵심 장면이고, 52.6% 보다 100% 가 그 구조를 정확히 드러낸다.
- 어휘와 계산이 이제 일치한다. 다음 사람이 같은 혼동에 다시 도달하지 않는다.

## 검토 과정에서 나온 반론 (기각됐지만 기록한다)

작성자는 처음에 **희석이 더 정확한 서술**이라고 판단했다. 전술망에서 데이터망을 잃어도
음성망이 살아 있으면 기동 통제는 저하될 뿐 불가능하지 않고, 음성망이 존재하는 이유가
그것이기 때문이다. 그 판단대로면 `hard` 를 넣되 아무 요구에도 표시하지 않게 된다.

과제 책임자가 **100% 로 확정**했다. 반론의 실질은 남아 있으므로 재검토 조건에 적는다:
음성 대체가 실질적으로 가능한 작업까지 hard 로 묶으면 임무 저하도가 쉽게 100% 에
붙고, 100% 가 흔한 상황도는 변별력을 잃는다. **tacnet 28스텝 중 몇 스텝이 100% 로
포화하는지를 계속 관측한다.** E2 가 noisyor 를 기각한 근거가 정확히 포화였다
(`docs/15` 5절).

## 결과

- 두 엔진(PowerShell 참조 구현, JS 포팅)에 `hard` 처리를 넣었다. `ui/tools/parity.mjs`
  로 두 구현이 여전히 일치하는 것을 확인한다.
- 두 시나리오의 `w = 1.0` 요구 12건(tacnet 8, defnet 4)에 `hard` 를 표시했다.
- `03-mission-ontology.md` 3절의 필드 설명을 갱신했다.
- **기존 실측 문서의 숫자를 전부 다시 만들었다**: `docs/11`, `docs/13`, `docs/15`,
  replay 데이터, 근거 팩과 브리핑. 숫자를 바꾸는 결정은 그 숫자를 인용한 모든 곳을
  같이 바꿔야 한다. 남겨두면 어느 것이 맞는지 아무도 모르게 된다.

## 대안

- **전파 함수를 max 로 바꾼다**: 기각. tacnet 28스텝 중 23스텝에서 noisyor 와 값이
  같아지고(포화), 최악 경로 밖 자산의 what-if 델타가 전부 0이 되어 봉쇄 비용 계산이
  무의미해진다(`docs/15` 6절, 9절).
- **`w = 1.0` 을 암묵적으로 hard 로 해석한다**: 기각. 시나리오 저자가 가중치를 1.0 으로
  적는 순간 의미가 바뀌는 함정이 된다. 명시 플래그를 쓰되 두 값을 함께 적는다.
- **아무것도 하지 않는다**: 기각. 이름과 계산이 어긋난 상태를 남기면 다음 사람이 같은
  결론에 다시 도달한다.

## 재검토 조건

- **포화 관측**: tacnet 시간축에서 100% 스텝 비율이 계속 오르면 hard 지정을 다시 본다.
  임무 저하도는 변별하라고 있는 값이지 경보를 크게 울리라고 있는 값이 아니다.
- 실무 검토에서 "이 작업은 음성 대체가 실제로 가능하다"는 판단이 나오는 요구가 있으면
  그 항목의 `hard` 를 내리고 근거를 시나리오 notes 에 적는다.
