# ADR-0005. 정규화 스키마는 OCSF

**상태**: 채택 (2026-09-05)

## 맥락

이 과제는 성격이 전혀 다른 소스를 동시에 다룬다: OpTC eCAR, LANL CSV, AIT 로그·PCAP,
시뮬레이터 이벤트, 장래의 실환경 SIEM/EDR. 소스마다 스키마가 다르면 상위 계층이 소스 수만큼
분기한다.

## 결정

**모든 이벤트를 OCSF로 정규화한 뒤에만 상위 계층에 올린다.**

- 위협 인텔 표현: STIX/TAXII
- 공격 기법 라벨: MITRE ATT&CK
- 소스별 어댑터는 `src/ingest/` 아래에 두고, 상위 계층은 OCSF만 안다.
- 원본 필드는 손실 없이 `unmapped` 확장 필드에 보존한다(정규화 과정에서 정보를 버리지 않는다).

## 근거

- OCSF는 벤더 중립적 핵심 보안 스키마를 제공하는 오픈소스 프레임워크로, 서로 다른 스키마를
  매핑해 수집과 정규화를 단순화한다.
- AI 기반 트리아지나 자율 조사 도구는 의미적으로 일관된 데이터를 전제로 한다. **정규화가
  선행 조건**이다. 프롬프트로 스키마 차이를 메우려 하면 토큰과 오류가 함께 는다.
- 장래 실환경 연동 시 벤더 종속을 피한다.

## 결과

- 소스별 매핑 작업이 초기 비용으로 발생한다. 데이터셋마다 매핑 테이블을 만들고 문서화한다.
- 매핑 커버리지(원본 필드 중 OCSF로 매핑된 비율)를 데이터셋별로 기록한다. 이 수치 자체가
  방법론 재현성의 근거가 된다.
- ATT&CK 라벨이 있는 데이터셋(DARPA TC)과 없는 데이터셋의 처리가 갈린다.

## 대안

- **자체 스키마**: 기각. 재현성과 외부 연동성을 모두 잃는다.
- **ECS(Elastic Common Schema)**: 기각. 벤더 중립성 면에서 OCSF가 낫고, 보안 도메인
  커버리지도 더 목적에 맞는다.

## 재검토 조건

OCSF가 전술망 특유의 이벤트 유형을 표현하지 못하는 것이 확인되는 경우(확장 프로파일 정의로
먼저 대응하고, 그것으로도 안 되면 재검토).
