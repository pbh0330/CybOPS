# ADR-0007. 온프렘 배치 전제 + 모델 어댑터 계층

**상태**: 채택 (2026-09-05)

## 맥락

군 과제 특성상 시연은 공개 데이터로 하더라도, 실전개하면 텔레메트리 반출 문제가 즉시
생긴다. 상용 API 기반으로 설계했다가 나중에 온프렘으로 바꾸면 지연시간과 성능 특성이 전부
달라지고, 그 시점에 아키텍처를 다시 짜야 한다.

## 결정

**처음부터 온프렘 배치 가능한 모델을 전제로 아키텍처를 잡는다.**

- `src/llm/` 아래에 모델 어댑터 계층을 둔다. 상위 코드는 어댑터 인터페이스만 안다.
- **모델 교체가 프롬프트 템플릿 + 평가셋 교체로 끝나야 한다.**
- 특정 벤더 API에만 있는 기능(전용 도구 호출 형식, 벤더 고유 파라미터)에 의존하지 않는다.
  공통 분모(메시지, 시스템 프롬프트, 스트리밍, 구조화 출력)만 쓴다.
- 개발 중 편의를 위해 API 모델을 써도 되지만, **평가(트랙 C)는 반드시 온프렘 후보 모델을
  포함**한다. 그래야 실전개 시 성능이 예측 가능하다.
- 설정은 `configs/models.yaml`에 두고 코드에 모델명을 하드코딩하지 않는다.

## 근거

- 텔레메트리는 그 자체가 민감 정보다. 외부 API로 나가는 순간 반출 심의 대상이 된다.
- 온프렘 모델은 API 모델 대비 지연·컨텍스트 길이·품질 특성이 모두 다르다. 뒤늦게 바꾸면
  프롬프트와 UX 예산을 전부 다시 잡아야 한다.
- 어댑터 계층은 평가 비교 실험(모델 3~4종)을 가능하게 하는 전제 조건이기도 하다.

## 결과

- 가용 GPU 사양이 모델 크기 선택을 제약한다. → `../99-open-questions.md` Q4
- 컨텍스트 길이 예산을 보수적으로 잡아야 한다. 긴 텔레메트리 덤프를 통째로 넣는 프롬프트
  설계를 하지 않는다(요약·검색으로 압축).
- 벤더 고유 기능을 못 쓰므로 일부 편의를 포기한다.

## 대안

- **API 우선, 나중에 이식**: 기각. 위 맥락대로 이식 비용이 아키텍처 재작업 수준이다.
- **온프렘 전용, API 완전 배제**: 과함. 개발 중 API 사용은 어댑터 뒤에 있는 한 문제없다.

## 재검토 조건

과제 대상이 실전개가 아닌 순수 연구용으로 확정되고, 텔레메트리 반출 제약이 없음이 명확해지는
경우.
