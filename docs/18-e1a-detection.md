# 18. E1-a 탐지 실험 - 설계와 방법

**대상**: LANL Comprehensive `auth.txt` + `redteam.txt`
**근거**: `02-research-plan.md` E1-a, `04-evaluation.md` 2.1, ADR-0008(accuracy 금지),
ADR-0011(LANL 라벨 재정의)
**상태**: **완료 (2026-09-08)**. 결과는 4절.

---

## 1. 무엇을 묻는가 - 그리고 무엇을 묻지 않는가

**묻지 않는 것: "레드팀을 탐지할 수 있는가."** 이미 풀렸고 값어치가 없다.

```
src in {C17693, C22409, C19932, C18025}   recall 100%
src == C17693 단독                          recall 93.6%
```

라벨의 출발지 호스트가 넷뿐이기 때문이다(`08-lanl-ground-truth.md`, ADR-0011).
**재현율은 공짜로 주어진다.**

**묻는 것: 그 규칙이 못 하는 것을 할 수 있는가.** 4개 호스트 규칙은 auth 48,079행을
집어 그중 702행만 맞는다 - **precision 1.46%, 참 1건당 오탐 67건**이다. 운영에서 못 쓴다.

> **E1-a 의 질문**
> 호스트·계정 신원을 쓰지 않는 행동 특징으로, 같은 재현율에서 저 정밀도를 넘을 수 있는가.

## 2. 신원 특징을 왜 원천 배제하는가

라벨 702건 중 **670건(95.4%)이 C17693 한 대**에 있다. 호스트 id 를 특징으로 주면 모델은
"C17693 을 외웠다"만으로 recall 93.6% 를 찍는다. **그 숫자는 아무것도 의미하지 않는다.**

그래서 나중에 드롭하지 않고 **애초에 파일에 넣지 않는다.** `Export-AuthFeatures.ps1` 은
호스트·계정 문자열을 상태 딕셔너리의 키로만 쓰고 정수로 인턴한 뒤 버린다. 출력 CSV 에
신원 컬럼이 없다. `run_e1a.py` 는 시작할 때 컬럼명에 `comp|user|host|id` 가 있으면
**학습을 거부하고 종료한다.** 없는 것은 샐 수 없다.

`04-evaluation.md` 의 호스트 프로파일 순위표(C17693 이 peers/event 상위 3.6%)도 같은
이유로 **특징 선택에 쓰지 않는다.** 그 표는 테스트 라벨을 보고 만든 것이라, 보고 특징을
고르면 답을 보고 답을 쓰는 것이다.

## 3. 방법

### 3.1 라벨

`redteam.txt` 749줄, **고유 715건**(중복 34줄, 4.5%). 중복을 먼저 제거한다 - 안 하면
같은 이벤트가 train 과 test 에 동시에 들어간다.

조인 키는 **4필드** `(time, src_user, src_computer, dst_computer)`. `04-evaluation.md`
가 정한 기본값이고, 3필드로 넓히면 14건이 목적지가 다른 행에 붙는다.

### 3.2 전수 순회 + 음성 부표본

**후보를 좁히지 않는다.** 트리비얼 규칙이 고른 48k 행만 재순위화하면, 그 후보 집합 자체가
**라벨의 출발지 호스트로 정의된 것**이라 나오는 정밀도가 정답에 조건부가 된다.

그래서 10.5억 행 전부를 순회하고 **음성만 1/500 로 부표본한다.** 양성은 전부 남긴다.
모든 지표는 **표본 가중치**로 계산한다 - 남은 음성 하나가 500개를 대표하므로, 가중
정밀도·PR-AUC 는 전수 채점과 같은 값이다.

> 가중치를 빼면 정밀도가 약 500배 부풀려진다. 재현이 안 되는 논문 수치는 대개 이렇게
> 만들어진다.

### 3.3 인과성 - 미래를 보지 않는다

이벤트의 특징은 **그 이벤트보다 엄격히 앞선** 상태로만 계산한다. 스트림은 시간순이고
상태 갱신은 방출 뒤에 일어난다.

"이번 시간대 접촉 목적지 수" 는 **"지금까지 이번 시간대"** 를 뜻하지 "이번 시간대 총합"
이 아니다. 후자면 공격의 첫 수를 채점하면서 나머지 공격을 이미 보고 있는 것이 된다.

창은 **시간 버킷**(`t / 3600`)이다. 진짜 슬라이딩 창은 키마다 타임스탬프 덱이 필요해
메모리가 수십 MB 에서 기가바이트가 되는데, 특징의 의미는 달라지지 않는다.

### 3.4 특징 목록 (18종, 확정)

원본이 68 GB 라 "그것도 뽑을걸" 이 한 번 더 전수 순회다. 쓰기 전에 확정한다(CLAUDE.md).

| 그룹 | 컬럼 | 뜻 |
|---|---|---|
| 출발지·시간대 | `src_hr_events` | 이번 시간대 이 출발지의 인증 수 |
| | `src_hr_dst` | 이번 시간대 접촉한 서로 다른 목적지 수 |
| | `src_hr_usr` | 이번 시간대 사용된 서로 다른 계정 수 |
| | `src_hr_failrate` | 이번 시간대 실패율 |
| | `src_prev_dst` | **직전** 시간대의 목적지 수 (급증 감지용) |
| 출발지·누적 | `src_life_events`, `src_life_dst` | 지금까지 누적 |
| 신규성 | `src_new_dst` | 이 (출발지,목적지) 조합이 처음인가 |
| | `src_new_usr` | 이 (출발지,계정) 조합이 처음인가 |
| 목적지 | `dst_hr_src`, `dst_life_src` | 이 목적지에 접속한 서로 다른 출발지 수 (팬인) |
| 계정 | `usr_hr_src`, `usr_life_src` | 이 계정이 쓰인 서로 다른 출발지 수 |
| | `usr_hr_failrate` | 계정 실패율 |
| 이벤트 자체 | `is_fail` | 실패 여부 |
| | `auth_*` (3) | NTLM / Kerberos / 그 외 |
| | `lt_*` (5) | Network / Service / Batch / Interactive / 그 외 |
| | `or_*` (5) | LogOn / LogOff / TGS / TGT / 그 외 |
| 시각 | `hour` | 하루 중 시각 (0-23) |

신원은 없다. 위 어느 것도 "어느 호스트인가" 를 말하지 않는다.

### 3.5 분할

**시간 단순 분할을 쓰지 않는다.** 749건의 75% 가 3일(8·12·13일차)에 몰려 있어 분할
지점 하나로 결과가 통째로 바뀐다(`04-evaluation.md`).

일 단위 캠페인 블록으로 나누고 **분할 지점을 훑어 민감도를 함께 보고** 한다. 한 지점만
보고하면 그 지점을 고른 것이 결과가 된다.

> 처음에 20/25/30/35 로 잡았다가 30과 35 에서 테스트 양성이 0건인 것을 보고 8/10/12/15
> 로 고쳤다. 레드팀은 29.6일차에 끝난다. 4.1절에 그대로 적었다.

한쪽에 양성이 20건 미만이면 그 분할은 **결과를 내지 않고 건너뛴다.** 양성 5건짜리
테스트셋의 PR-AUC 는 숫자이지 측정이 아니다.

### 3.6 비교 대상

| | 신원 사용 | 비고 |
|---|---|---|
| 트리비얼 규칙 (4개 호스트) | **예** | 필수 보고 행. 모델이 못 보는 것을 본다 |
| 행동 규칙 `hr_dst x (1+hr_failrate)` | 아니오 | 사람이 제일 먼저 시도할 규칙 |
| Linear SVM | 아니오 | 선행 실측에서 최강 베이스라인이었던 계열 |
| Logistic Regression | 아니오 | |
| Gradient Boosting (HistGB) | 아니오 | |

**학습 모델이 행동 규칙을 못 이기면 학습이 일을 하는 게 아니다.**

### 3.7 지표

`04-evaluation.md` 2.1 그대로. **accuracy 는 쓰지 않는다**(ADR-0008).

- **PR-AUC** (가중)
- **precision@recall{50,90,100}** - 같은 재현율에서 트리비얼 규칙의 1.46% 와 직접 비교
- **alerts@recall** - 그 재현율을 얻는 데 분석관이 봐야 하는 건수
- **precision@k** (k = 100 / 1,000 / 10,000 실경보)

## 4. 결과

### 4.1 먼저 잡힌 두 가지 - 둘 다 설계 오류였다

**(1) 처음 잡은 분할 20/25/30/35 중 두 개는 테스트 양성이 0건이었다.**

라벨 분포를 뽑고서야 봤다. 레드팀은 1.75~29.6 일차에만 있고 8일차 261건, 12일차 207건에
몰려 있다.

```
day  8   261  ################################
day 12   207  #########################
day 13    75  #########
day 29    10  #
```

| 분할 | 학습 양성 | 테스트 양성 |
|---|---|---|
| 8 | 311 | 391 |
| 10 | 316 | 386 |
| 12 | 523 | 179 |
| 15 | 649 | 53 |
| **30** | 702 | **0** |

**분할을 정하기 전에 라벨 분포부터 봤어야 했다.** `04-evaluation.md` 가 "749건의 75%가
3일에 몰려 있다" 고 이미 적어뒀는데 그것을 분할 설계에 반영하지 않았다. 쓸 수 있는
분할은 8~15 뿐이다.

**(2) 부표본 하에서 precision@k 는 작은 k 에서 매우 불안정하다.**

음성을 1/500 로 남겼으므로 남은 음성 하나가 가중치 500이다. 가중 경보예산 k=1,000 은
**샘플된 음성 약 2행**만에 도달한다. 점추정은 불편추정이지만 그 두 행에 얹혀 있다 -
그것들이 대표하는 실제 음성 1,000건이 진짜 양성 위에 있는지 아래에 있는지는 관측되지
않았다.

신뢰구간 없이 "4.03%" 를 적는 것은 표본이 뒷받침하지 못하는 정밀도를 주장하는 것이다.
부트스트랩(음성만 재표집, 양성 702건은 표본이 아니라 전수)을 넣었다.

### 4.2 pass-1 (원시 카운트 18종)

분할별 GBDT. 트리비얼 규칙은 순위가 없으므로 어느 k 에서든 정밀도가 1.46% 로 일정하다.

| 분할 | PR-AUC | P@재현50% | P@1000경보 |
|---|---|---|---|
| 8 | 0.00073 | 0.05% | 0.0% |
| 10 | 0.00529 | 0.06% | **4.03%** |
| 12 | 0.00437 | 0.05% | **3.38%** |
| 15 | 0.00444 | 0.04% | **3.29%** |
| *트리비얼(신원 사용)* | - | - | *1.46%* |

읽어야 할 것.

1. **경보예산 기준으로는 이미 이겼다.** k=1,000 에서 3.3~4.0% 대 1.46% 로 2.3~2.8배다.
   `04-evaluation.md` 가 precision@k 를 "SOC 현실 지표 - 분석관이 하루에 볼 수 있는
   건수" 로 둔 이유가 여기 있다. **그리고 이것은 신원을 전혀 쓰지 않고 나온 값이다.**
2. **재현율 기준으로는 완패다.** P@재현50% 가 0.05% 다. 라벨 절반을 얻으려면 경보가
   수만 건 필요하다. 트리비얼 규칙은 48,079건으로 재현율 100% 를 준다.
3. **분할 8 에서 무너진다.** 학습 양성 311건으로는 학습이 안 된다. `04-evaluation.md`
   가 요구한 민감도 보고가 바로 이것이고, 최고값만 적으면 그 분할을 고른 것이 결과가
   된다.
4. 행동 규칙 `hr_dst x (1+failrate)` 는 전 분할에서 PR-AUC ~0 이다. 사람이 제일 먼저
   시도할 규칙이 안 통한다는 뜻이고, 학습이 실제로 일을 하고 있다는 뜻이기도 하다.

### 4.3 pass-2 (자기 기준선 대비, 45종)

| pass | 분할 | 검증 PR-AUC | 테스트 PR-AUC | P@재현50% | P@100 (95% CI) | P@1000 (95% CI) |
|---|---|---|---|---|---|---|
| 1 | 10 | 0.045 | 0.00529 | 0.06% | - | 4.03% |
| **2** | 10 | **0.231** | 0.00407 | 0.00% | **6.19% [2.2, 6.2]** | 3.19% [1.3, 3.3] |
| 1 | 12 | 0.010 | 0.00437 | 0.05% | - | 3.38% |
| **2** | 12 | **0.138** | 0.00514 | **0.44%** | 4.21% [1.4, 100] | **11.74% [1.4, 11.7]** |
| *트리비얼* | | | | | *1.46%* | *1.46%* |

**(1) 검증에서는 5~14배 올랐다.** 자기 기준선 대비 특징이 실제로 신호를 준다.

**(2) 그 이득이 테스트로 다 넘어오지 않았다.** 분할 12 에서는 P@1000 이 3.38% -> 11.74%
(3.5배), P@재현50% 가 0.05% -> 0.44% (9배)로 크게 올랐다. 분할 10 에서는 오히려 살짝
내려갔다.

검증 폴드는 0~10일 안에 있고 테스트는 10~58일이다. **호스트별 러닝 평균·표준편차는 이력이
쌓여야 의미가 생기므로**(`n < 3` 이면 z 를 0으로 반환한다) 초반 구간과 후반 구간에서 특징의
분포 자체가 다르다. 캠페인 경계를 넘어 일반화되지 않은 것이다.

**이것은 테스트로 튜닝하지 않았기 때문에 보인다.** 테스트를 보고 골랐으면 분할 12 의
11.74% 를 집어 "8배 개선" 이라고 적었을 것이다.

**(3) 그리고 그 11.74% 는 지금 표본으로는 주장할 수 없다.**

95% 신뢰구간의 하한을 보면 트리비얼 기준선 1.46% 를 확실히 넘는 것은 **분할 10 의
P@100 = 6.19% [2.2%, 6.2%]** 하나뿐이다. 나머지는 구간이 1.46% 를 포함한다. 분할 12 의
P@100 은 상한이 100% 로 구간이 무의미하다.

> **지금 병목은 모델이 아니라 측정이다.** 음성을 1/500 로 남긴 탓에 작은 k 에서
> 추정이 샘플 두어 행에 얹혀 있다. 구간을 좁히는 방법은 모델을 더 만지는 것이 아니라
> 음성을 더 촘촘히 뽑는 것이다.

### 4.4 조밀 표본 + 누적 특징 절제 - 확정 결과

음성을 1/100 으로 5배 조밀하게 다시 뽑고(1,050만 행), 전체 탐색으로 돌렸다.
그리고 **누적 특징 7종을 뺀 절제 실험**을 함께 돌렸다.

#### 왜 절제 실험을 했는가

`src_life_events`, `src_life_dst`, `src_life_failrate`, `pair_seen` 같은 누적값이
**호스트 지문으로 작동할 수 있다고 의심했다.** 라벨 702건 중 670건이 출발지 한 대에
몰려 있으니, 모델이 "누적 프로파일이 이런 호스트" 를 학습하면 이름 대신 통계로 신원을
재식별한 것이고, 그것은 ADR-0011 이 막으려던 실패를 뒷문으로 하는 것이다.

#### 의심은 틀렸고, 반대였다

| 분할 | 단위 | PR-AUC 전체 -> 누적제거 | P@100 전체 -> 누적제거 | >기준 |
|---|---|---|---|---|
| 8 | event | 0.005 -> **0.024** | 0% -> **9.09% [3.2, 15.3]** | no -> **yes** |
| 10 | event | 0.025 -> **0.100** | 2.91% -> **6.54% [2.3, 10.0]** | no -> **yes** |
| 12 | event | 0.136 -> **0.230** | 10.71% -> **28.06% [11.4, 100]** | yes -> **yes** |
| 15 | event | 0.714 -> **0.762** | 35.90% -> **37.11% [13.0, 37.5]** | yes -> **yes** |

**8개 행 전부가 기준선을 넘는다**(전체 특징일 때는 8개 중 3개였다).

누적 특징은 지문이 아니라 **잡음**이었다. 생애 누적값은 시간이 갈수록 커지기만 하므로
학습 구간과 테스트 구간의 분포 자체가 다르다. 모델이 그 드리프트를 신호로 착각했고,
빼고 나니 자기 기준선 대비 z 같은 진짜 행동 신호가 드러났다.

**4.3절에서 "검증은 5~14배 올랐는데 테스트가 안 따라온다" 고 적은 것의 원인이 이것이다.**

#### 확정 수치 (dense-nolife: 음성 1/100, 특징 38종, 신원·누적 전부 미사용)

| 분할 | 학습 양성 | 테스트 양성 | PR-AUC | P@재현50% | P@100 (95% CI) | P@1000 (95% CI) |
|---|---|---|---|---|---|---|
| 8 | 50 | 652 | 0.024 | 0.40% | 9.09% [3.2, 15.3] | 3.85% [2.4, 4.8] |
| 10 | 316 | 386 | 0.100 | 9.68% | 6.54% [2.3, 10.0] | **15.01% [7.3, 16.0]** |
| 12 | 316 | 386 | 0.230 | 21.61% | **28.06% [11.4, 100]** | 20.24% [12.4, 21.3] |
| 15 | 623 | 79 | **0.762** | **100%** | **37.11% [13.0, 37.5]** | 6.37% [4.8, 6.4] |
| *트리비얼* | | | | | *1.46%* | *1.46%* |

**신원을 전혀 쓰지 않고 트리비얼 규칙의 10~25배 정밀도**를 얻는다. 95% 구간 하한이
전부 1.46% 를 넘으므로 표본이 뒷받침하는 주장이다.

호스트-시간 단위(보조 지표)도 전 분할에서 기준선을 넘는다. 분할 12 에서 PR-AUC 0.407.

#### 그대로 적어야 할 것

- **분할 8 은 학습 양성이 50건뿐이다.** P@100 9.09% 가 나왔지만 양성 50건으로 학습한
  모델의 값이라 다른 분할과 같은 무게로 읽으면 안 된다.
- **분할 15 는 테스트 양성이 79건이다.** PR-AUC 0.762 와 재현율 50%까지 정밀도 100% 는
  79건 위에서 나온 값이다.
- **분할 간 분산이 pass 간 차이보다 크다.** 이것이 `04-evaluation.md` 가 민감도 보고를
  요구한 이유이고, 한 분할만 골라 적으면 그 분할을 고른 것이 결과가 된다.

### 4.5 무엇이 신호를 만드는가 - 그리고 NTLM 단독은 아무것도 아니다

순열 중요도(`scripts/e1a_importance.py`)로 잰 상위 특징이다. 트리 내부 분할 횟수가 아니라
**컬럼을 섞고 지표가 얼마나 떨어지는가**로 잰다 - 분할 횟수는 고카디널리티 컬럼을
예측력과 무관하게 상위로 올린다.

| 분할 | 1위 | 2위 | 3위 | 4위 |
|---|---|---|---|---|
| 8 | `auth_ntlm` 36.6% | `src_hr_dst_share` 14.4% | `is_fail` 10.1% | `usr_hr_dst` 8.3% |
| 10 | `src_hr_newdst_share` 25.3% | `auth_ntlm` 22.8% | `src_hr_dst_z` 13.6% | `src_gap_log` 8.1% |
| 12 | `auth_ntlm` 23.3% | `usr_hr_dst` 9.7% | `src_hr_dst_z` 9.1% | `src_hr_newdst_share` 8.9% |
| 15 | `auth_ntlm` 36.3% | `src_hr_events` 14.2% | `src_hr_dst_share` 11.6% | `src_hr_dst_z` 10.2% |

`auth_ntlm` 이 전 분할에서 최상위다. **그러면 "레드팀이 NTLM 을 썼다" 가 결론 아닌가?**
확인했다.

| 분할 | NTLM 단독 PR-AUC | 학습 모델 PR-AUC | P@100 (NTLM 단독) |
|---|---|---|---|
| 8 | 0.00002 | 0.02429 | **0.00%** |
| 10 | 0.00001 | 0.09960 | **0.00%** |
| 12 | 0.00001 | 0.23030 | **0.00%** |
| 15 | 0.00000 | 0.76227 | **0.00%** |

`is_fail` 단독, `NTLM + 실패율`, `NTLM + 첫접촉비중`, `NTLM + 팬아웃 z` 도 전부 P@100 이
0.00% 다. NTLM 은 정상 트래픽에 널려 있어 **그 자체로는 후보를 좁히지 못한다.**

**즉 `auth_ntlm` 은 필요조건이지 신호가 아니다.** 순열 중요도에서 1위인 이유는 그것을
섞으면 나머지가 무너지기 때문이지 그것만으로 무엇을 할 수 있어서가 아니다. 일하는 것은
**조합**이다 - 자기 대비 팬아웃 급증(`src_hr_dst_z`), 첫 접촉 비중
(`src_hr_newdst_share`), 시간대 실패율, 이벤트 수가 NTLM 조건 위에서 결합될 때만 작동한다.

`04-evaluation.md` 가 기여 지점으로 적어둔 문장 그대로다: **"다변량 결합과 시간 문맥으로
상위 3.6% 를 상위 0.01% 로 좁힐 수 있는가."**

> 중요도 표의 절대 수준은 인용하지 않는다. 순열 루프는 음성 30만 부표본 위에서 돌고,
> 부표본은 정밀도를 위로 편향시킨다(`e1a_importance.py` 주석). 보고용 PR-AUC 는 전체
> 테스트셋 값이고 평가 JSON 과 일치한다. 표에서 읽는 것은 **순위와 기여 비중**이다.

### 4.6 왜 pass-2 가 필요했는가

pass-1 의 실패가 pass-2 의 근거다. `04-evaluation.md` 가 이미 적어둔 그대로다 -
C17693 은 peers/event 상위 3.6% 지만 그보다 높은 정상 호스트가 644대 있다.
**원시 카운트는 "바쁜 호스트" 와 "평소와 다른 호스트" 를 구분하지 못한다.** 파일서버는
원래 매시간 수백 대와 통신한다.

pass-2 는 자기 기준선 대비 이탈을 넣는다(3.4절 표 참조). 결과는 나오는 대로 적는다.
