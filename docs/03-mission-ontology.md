# 03. 임무-자산 온톨로지 (L2) - 상황도의 좌표계

공개 데이터에 존재하지 않으므로 자체 정의한다. 이것이 이 과제에서 **기술적으로 가장 어렵지는
않지만 공수가 가장 많이 드는 공정**이다.

## 1. 왜 이것이 좌표계인가

지리 지도에서 "위치"가 좌표를 주듯, 사이버 상황도에서 의미 있는 좌표는 **그 자산이 어떤
임무를 얼마나 떠받치고 있는가**이다.

- crown jewels 분석: 임무 핵심 기능을 직접 수행하거나, 다른 핵심 자산에 대한 접근·보호·동작을
  가능하게 하는 자산을 식별한다.
- 영향 의존성 그래프: 자산·서비스·임무·임무 단계와 그 의존관계를 담는다.
- 임무-작업-자산(MTCM) 모델에서 사이버 위협의 영향을 임무 수준 심각도로 전파하는 계산 방식이
  이미 제안되어 있다.

이 그래프가 지형이고, 자산이 지물이며, 임무 저하도가 등고선이다.

## 2. 노드 타입

| 타입 | 설명 | 핵심 속성 |
|---|---|---|
| `Mission` | 최상위 임무 | id, name, priority, commander, timeframe |
| `Phase` | 작전 단계 | id, mission_id, sequence, start/end |
| `Task` | 작업 | id, phase_id, criticality, min_capability |
| `Service` | 논리 서비스 (지휘통제, 통신, 정보공유 등) | id, name, **kind**, sla, redundancy_group |
| `Asset` | 물리·논리 자산 (호스트, 네트워크 장비, 앱) | id, type, owner_unit, geo(8절), ocsf_ids |
| `Unit` | 부대·조직 | id, echelon, parent_unit |

`Service.kind`는 서비스의 종류다: `messaging`, `voice`, `fire-control`, `position-reporting`,
`intel`, `directory`, `file`, `database`, `web`, `mail`, `logistics`. 화면에서 서비스를
구분하는 근거이자, 시나리오를 편집할 때 **어떤 서비스가 서로 대체 가능한가**를 판단하는
기준이다. 이름만으로는 그 판단을 할 수 없다.

`Asset.geo`는 **자산의 물리적 위치**다. 외부 IP 지오로케이션과 혼동하지 않는다.
전자는 신뢰할 수 있는 대장 정보, 후자는 판단에 쓰지 않는 참고값이다. (ADR-0002)
전술망에서는 이 값이 시간축을 탄다. 스키마는 8절, 설계 근거는
[17-geo-layer.md](17-geo-layer.md)에 있다.

## 3. 엣지 타입

| 엣지 | 방향 | 의미 | 가중치 |
|---|---|---|---|
| `part_of` | Phase→Mission, Task→Phase | 구성 | - |
| `requires` | Task→Service | 작업이 서비스를 요구 | 필수도 w∈[0,1] |
| `provided_by` | Service→Asset | 서비스가 자산 위에서 제공됨 | 기여도 |
| `depends_on` | Asset→Asset | 자산 간 의존 (DB→앱 등) | 강도 |
| `hosted_on` | Asset→Asset | VM→호스트, 컨테이너→노드 | - |
| `communicates_with` | Asset↔Asset | 통신 경로 (공격 확산 경로 후보) | - |
| `redundant_with` | Asset↔Asset | 이중화 그룹 | - |

`redundant_with`가 저하도 계산의 난이도를 결정한다. 이중화가 있으면 자산 1개 침해가 임무
저하로 직결되지 않는다. 이 처리를 빼먹으면 상황도가 과잉 경보를 낸다.

## 4. 임무 저하도 전파

자산 상태 → 서비스 가용도 → 작업 수행도 → 임무 저하도 순으로 올린다.
전파 함수는 **명시적 수식으로 문서화하고 코드와 1:1 대응시킨다.** LLM이 관여하지 않는다.
(ADR-0003)

후보 방식 (트랙 B에서 비교 실험):

1. **가중 최소경로 / max-flow**: 이중화를 흐름 용량으로 모델링. 직관적이고 설명 가능.
2. **noisy-OR**: 여러 자산 침해가 서비스에 미치는 영향을 확률적으로 합성. 불확실성 표현에 유리.
3. **최대치 전파(max-propagation)**: 가장 단순. 베이스라인으로 둔다.

선택 기준은 정확도가 아니라 **설명 가능성**이다. 지휘관이 "왜 이 임무가 붉은가"를 물었을 때
3단계 안에 답할 수 있어야 한다.

산출 형태:
```
mission_degradation(m, t) ∈ [0, 1]
  + 기여 상위 k개 자산·경로 (설명용)
  + 확신도 (근거 이벤트의 확신도에서 유래)
```

## 5. 데이터 조달 - 어떻게 만들 것인가

L2에는 공개 데이터가 없으므로 아래 순서로 **합성**한다.

1. **템플릿 임무 정의**: 공개된 교리·표준 문서 수준의 일반적 임무 구조를 참고해 2~3개
   임무 시나리오를 정의한다. 실제 부대 편성이나 실제 임무 계획은 쓰지 않는다(비밀 문제).
2. **L1 자산 인벤토리 추출**: OpTC/LANL/AIT의 호스트·계정 목록을 뽑아 `Asset` 노드로 만든다.
   여기가 L1↔L2 조인 지점이다.
3. **역할 부여 규칙**: 관측된 행위 패턴으로 자산 역할을 추정한다(포트 445 다수 수신 → 파일서버,
   LDAP 트래픽 집중 → 도메인 컨트롤러 등). 규칙 기반 초안 → 수작업 보정.
4. **의존 엣지 생성**: `communicates_with`는 관측 플로우에서 자동 생성. `requires`,
   `provided_by`는 수작업 정의.
5. **MSDL 등 표준 정렬 검토**: 임무-작업-자산 모델을 SISO 군용 시나리오 정의 언어(MSDL) 같은
   표준으로 추상화하는 선행 제안이 있다. 논문 기여도를 위해 정렬 가능성을 검토한다.

> **비밀 취급 주의**: 이 저장소의 임무 모델은 전부 공개 데이터와 일반 교리 수준에서 구성한
> 가상 시나리오다. 실제 부대 편성·임무 계획·자산 대장을 이 저장소에 넣지 않는다.

## 6. 표현 형식

- 저장: JSON-LD 또는 YAML + 스키마 검증. 그래프 DB는 규모상 초기엔 불필요.
- 파일: `data/processed/mission/<scenario>/{nodes,edges}.yaml`
- 검증: 순환 의존 탐지, 고아 노드 탐지, 가중치 범위 검사 → CI에서 돌린다.

## 7. 시간축 (전술망 확정으로 필수가 됨)

ADR-0012로 대상 망이 전술망으로 확정되면서 정적 그래프로는 부족해졌다. 노드가 이동하고
링크가 끊겼다 붙는다. 스키마와 계산 규칙은 [ADR-0017](adr/0017-temporal-mission-graph.md),
실측 결과는 [11-tactical-time-axis.md](11-tactical-time-axis.md)에 있다. 요약만 적는다.

### 7.1 추가 필드

| 위치 | 필드 | 의미 |
|---|---|---|
| 루트 | `timeline` | `{unit, t0_iso, horizon, step}`. 이 블록이 있으면 시간축 모드다 |
| `Phase` | `window {from,to}` | 그 단계가 활성인 반열린구간 `[from, to)` |
| `Asset` | `outages[]` | `{from, to, cause, note}` 비가용 구간 |
| `Asset` | `mobility` | `static` / `mobile` (표시·설명용) |
| `Asset` | `transit` | 남의 트래픽을 중계하는가. 기본 true, **종단 단말은 false** |
| `Asset` | `geo` | 위치. 정지는 고정 좌표, 기동은 구간별 좌표. 8절 |
| `Task` | `performed_at` | 작업이 수행되는 자산. 도달성 계산의 출발점 |
| 루트 | `links[]` | `{id, a, b, bearer, outages}`. 전술망에서 `communicates_with`를 대체 |

시간 값은 전부 `t0_iso`로부터의 경과(분)다. 절대시각을 쓰지 않는다 - 시나리오를 다른
날짜로 재사용할 수 있어야 한다.

### 7.2 원인 라벨 - 이것이 전술망의 핵심 요구다

`attack` / `mobility` / `terrain` / `maintenance` / `unknown`.

**`outages`에는 `attack`을 쓰지 않는다.** 공격 상태는 별도의 침해 상태 입력으로만 들어온다.
검증기가 이 위반을 오류로 잡는다. 두 경로를 섞으면 "이 저하가 적의 소행인가"를 계산으로
답할 수 없게 된다.

`unknown`은 공격으로 승격되지 않는다. 재밍인지 기상인지 모르는 단절은 끝까지 `unknown`이다.

### 7.3 계산에서 달라지는 것

- 시점 t의 임무 저하도는 **t에 활성인 단계의 작업만** 집계한다. 활성 단계가 없으면
  0이 아니라 **미정의**다.
- **도달성이 이중화보다 먼저다.** 작업 수행 단말이 서비스 제공 자산에 닿지 못하면 그
  제공자는 죽은 것과 같다. 도달 불가능한 이중화는 이중화가 아니다.
- **작업은 자기가 돌아가는 단말보다 좋을 수 없다**: `task_deg >= impact(performed_at)`.
- 저하도는 `total` / `attack` / `env` / `inter`로 분해해 보고한다(ADR-0017 4항).

### 7.4 검증기가 잡는 것

`scripts/Test-Ontology.ps1`이 시간축 시나리오에 대해 추가로 검사한다.

- 구간 유효성(`from < to`, horizon 초과), 단계 사이의 빈 시간(경고)
- 원인 라벨이 정의된 5종인지, `cause=attack`을 쓰지 않았는지
- `performed_at` 존재 여부
- **정적 도달성**: 모든 링크가 살아 있다고 가정해도 작업이 요구 서비스에 닿지 못하면 오류

## 8. 지리 스키마 (보조 레이어)

**기본 뷰는 여전히 임무 그래프다(ADR-0001).** 지리는 토글 가능한 보조 레이어이고,
지도를 주화면으로 만드는 설계를 하지 않는다. 어떤 판단 로직도 이 절의 필드를 읽지 않는다.
설계 근거·안전성 논거·한계는 [17-geo-layer.md](17-geo-layer.md)에 있다. 스키마만 적는다.

### 8.1 좌표계는 3층이고 저장하는 것은 하나다

| 층 | 값 | 저장 |
|---|---|---|
| 정본 | 로컬 평면 (미터, x=동, y=북, z=표고 MSL) | **그렇다** |
| 지도 배치 | WGS84 위경도 | 아니다. 앵커 + 변환식에서 파생 |
| 표시 | MGRS 문자열 | 아니다. 위경도에서 파생 |

자산마다 두 표현을 각각 저장하면 어긋난다. **자산당 정본 좌표는 하나다.**
MGRS는 WGS84 datum 기반이라 위경도에서 무손실로 파생되지만, 반대로 저장 정본으로 쓰면
자릿수가 곧 정밀도라 값이 잘리고 격자 경계에서 보간이 깨진다. 그래서 표시 전용이다.

### 8.2 루트 `geo` 블록

| 필드 | 의미 |
|---|---|
| `geo.frame` | 정본 평면 정의: `id`, `kind: "local-plane"`, `unit`, `axes`, `extent` |
| `geo.georef` | 평면 -> WGS84 앵커와 변환식, 근사 오차, `mgrs` 표시 정책 |
| `geo.safety` | 가상 좌표임을 보증하는 논거와 **배경지도 정책** |
| `geo.terrain` | 능선·계곡 등 도식. **서술 전용. 엔진이 읽지 않는다** |
| `geo.position_rule` | 시점 t의 좌표를 뽑는 결정론 규칙(8.4)을 데이터로 중복 기재 |

### 8.3 `Asset.geo` - 정지와 기동

정지 자산은 고정 좌표, 기동 자산은 ADR-0017의 반열린구간 `[from, to)` 표기를 그대로 쓴다.

```json
"geo": {"kind": "fixed", "frame": "TACGRID-01", "source": "asset-register",
        "accuracy_m": 15, "at": {"x": 10400, "y": 10900, "z": 418}}
```

```json
"geo": {"kind": "track", "frame": "TACGRID-01", "source": "asset-register",
        "accuracy_m": 25, "segments": [
  {"from": 0,   "to": 95,  "mode": "hold", "at": {"x": 8622, "y": 8192, "z": 146}},
  {"from": 95,  "to": 125, "mode": "move", "at":    {"x": 8622,  "y": 8192,  "z": 146},
                                           "to_at": {"x": 13842, "y": 12432, "z": 205}},
  {"from": 125, "to": 420, "mode": "hold", "at": {"x": 13842, "y": 12432, "z": 205}}
]}
```

`kind` 는 `mobility` 와 대응한다: `static` -> `fixed`, `mobile` -> `track`.
`source` 는 이 값이 어디서 왔는지다(`asset-register`). 8.6절 참조.

### 8.4 시점 t의 좌표 (결정론)

1. `fixed` 이면 언제나 `at`.
2. `track` 이면 `from <= t < to` 인 구간을 찾는다. 구간은 겹치지 않고 `[0, horizon)` 을
   빈틈없이 덮는다.
3. `hold` 이면 구간 내내 `at`.
4. `move` 이면 `u = (t - from) / (to - from)` 으로 `at` 과 `to_at` 을 성분별 선형보간한다.
   x, y, z 전부 같은 `u`.
5. 어떤 구간에도 없으면 0도 마지막 값도 아닌 **미정의**다. "위치 미상"으로 표기한다.
   ADR-0017의 "활성 단계 없으면 저하도 미정의"와 같은 태도다. 마지막 위치를 그대로 찍는
   상황도는 없어진 부대를 살아 있는 것처럼 그린다.

### 8.5 `geo` 와 `outages` 는 직교한다

**outage 중이어도 위치는 정의된다.** 미전개 장비도 어딘가에는 있다. 반대로 좌표가
움직인다고 outage 가 생기지도 않는다. 두 값의 정합은 저작자가 수작업으로 맞춘 것이고
계산되지 않는다. **가시선·차폐를 좌표에서 유도하지 않는다** - 기하가 원인 라벨을 만들기
시작하면 "지형인가 재밍인가"를 구분할 수 없어지고, 이는 ADR-0017 3항의 취지를 깎는다.

### 8.6 `Asset.geo` 는 IP 지오로케이션이 아니다

| | `Asset.geo` | `enrichment.geo.country` |
|---|---|---|
| 붙는 곳 | 자산 (mission.json) | 이벤트 (OCSF 정규화 결과) |
| 출처 | 자산대장 / 기동계획 | 외부 IP 지오로케이션 DB |
| 정밀도 | 미터 (`accuracy_m`) | **국가 코드까지만** |
| 판단에 쓰는가 | 아니다. 임무 중요도는 그래프가 낸다 | 아니다. 값이 체계적으로 틀린다 (ADR-0002) |

**둘을 같은 필드에 넣지 않는다.** 스키마상으로도 파일이 분리되어 있다.

## 9. 열린 질문

- 심볼 체계는 MIL-STD-2525 준용으로 확정됐다(ADR-0013). `Asset.type` → SIDC 매핑 테이블이
  이 스키마의 일부로 들어와야 한다.
- 베어러별 서비스 구분(음성망/데이터망)이 없다. 현재는 링크를 무차별 전송로로 본다.
- 링크 용량·지연이 없다. 저대역폭에서의 **성능 저하**(끊김이 아니라 느려짐)는 미모델링.
- 단절 원인 라벨의 실제 출처(기동계획·지형·무전기 상태)가 없으면 전부 `unknown`이 된다.
  `unknown` 비율이 높을 때 상황도가 무엇을 보고할지 미정.
