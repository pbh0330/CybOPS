# 17. 지리 레이어 - 좌표계, 시간축 위 위치, 가상 좌표 안전성

`scenarios/tacnet-01/mission.json` 에 들어간 `geo` 블록의 설계 근거와 한계를 적는다.
스키마 요약은 [03-mission-ontology.md](03-mission-ontology.md) 8절에 있다.

**이 문서는 데이터 계층만 다룬다.** UI 구현은 여기 없다.

## 1. 이 레이어의 지위 - 보조다

**기본 뷰는 임무-자산 의존성 그래프다(ADR-0001).** 지리는 토글 가능한 보조 레이어다.
이 문서로 다음을 제약으로 못박는다.

- **지도를 주화면으로 만드는 설계를 하지 않는다.** 지도가 전체 화면을 차지하고 그래프가
  사이드 패널로 밀려나는 시안은 ADR-0001 위반이다. `06-design-workflow.md` 7절과 같은 규칙이다.
- **어떤 판단 로직도 `geo` 를 읽지 않는다.** 임무 저하도, 우선순위, 색상 등급, what-if
  모두 `geo` 없이 계산되고, 실제로 `scripts/Invoke-MissionPropagation.ps1` 은 이 필드를
  읽지 않는다(아래 7절 실측).
- 지리 레이어가 답하는 질문은 하나뿐이다: **"화면에서 빨간 그 노드는 지금 어디 있는가."**
  왜 빨간지는 그래프가 답한다.

전술망 확정(ADR-0012)으로 이 레이어의 값어치가 올라간 것은 사실이다. 노드가 실제로
움직이고, 링크가 죽는 흔한 이유가 기동과 지형이기 때문이다. 그러나 그것은 **지도가
필요하다**는 뜻이지 **지도가 주화면이어야 한다**는 뜻이 아니다.

## 2. 좌표계 - 3층으로 나눈다

| 층 | 값 | 저장하는가 | 쓰는 곳 |
|---|---|---|---|
| 정본 | 로컬 평면 `TACGRID-01` (미터, x=동, y=북, z=표고) | **그렇다. 유일한 정본** | 시나리오 저작, 보간, 거리 계산 |
| 지도 배치 | WGS84 위경도 | **아니다. 앵커에서 파생** | 지도 위젯, 투영 |
| 표시 | MGRS 문자열 | **아니다. 위경도에서 파생** | 화면 라벨, 구두 보고 형식 |

### 2.1 왜 로컬 평면이 정본인가

자산마다 위경도를 따로 저장하고 로컬 좌표도 따로 저장하면 **둘이 어긋난다.** 이 저장소는
같은 이유로 이미 한 번 선을 그었다 - 전파 엔진을 UI에 재구현하지 않고 미리 계산한
숫자만 내려보낸다(`scripts/Export-ReplayData.ps1` 머리말, ADR-0003). 좌표도 같다.
**자산당 정본 좌표는 하나다.**

로컬 평면을 고른 추가 이유가 하나 더 있다. 이 시나리오의 지형은 창작물이다. 능선과
계곡이 outage 의 원인 라벨(`terrain`)을 떠받치는데, 그 능선은 지구 어디에도 없다.
창작 지형은 **창작 평면 위에 있어야 자기모순이 없다.** 실제 위경도를 정본으로 잡는
순간 "여기 능선이 있다"는 서술이 실제 지형과 충돌한다.

### 2.2 왜 WGS84 를 정본으로 쓰지 않는가

지도 라이브러리는 전부 위경도를 먹으므로 위경도 자체는 필요하다. 다만 **파생값으로**
필요하다. `geo.georef` 가 변환식을 명시한다.

```
lat = anchor.lat + y / 111320
lon = anchor.lon + x / (111320 * cos(anchor.lat))
```

- 앵커: `lat 36.45, lon 128.500` = 로컬 `(0, 0)`
- 등장방형(equirectangular) 근사다. `cos` 를 앵커 위도에 고정하므로 AO 북쪽 가장자리
  (`y = 18000`)에서 동서 방향 최대 **약 90 m** 왜곡이 생긴다. 24 km x 18 km 상자에서
  0.4% 수준이고, 이 레이어는 표시용이므로 허용한다. **판단 로직은 로컬 평면 값만 쓴다**
  (읽는 판단 로직이 애초에 없다).
- 정밀한 배치가 필요해지면 등장방형을 지역 접평면(ENU)으로 바꾼다. 변환식이 `georef`
  한 곳에만 있으므로 그 교체는 데이터 재저작 없이 끝난다.

AO 네 모서리의 위경도:

| 로컬 | lat | lon |
|---|---|---|
| (0, 0) | 36.450000 | 128.500000 |
| (24000, 0) | 36.450000 | -123.271049 |
| (0, 18000) | -48.888304 | 128.500000 |
| (24000, 18000) | -48.888304 | -123.271049 |

### 2.3 MGRS 병기는 자연스러운가 - 그렇다. 단 표시 전용으로

**조사 결과: 자연스럽다.** MGRS는 NATO 군의 지리참조·위치보고 표준 좌표 형식이고
(STANAG 2211로 인용된다), UTM/UPS에서 파생되며 **WGS84 datum 기반**이다. 정밀도는
자릿수로 표현된다: 4자리 = 1 km, 6자리 = 100 m, 8자리 = 10 m, 10자리 = 1 m.

그러나 **저장 정본으로는 부적합하다.**

- **정밀도가 문자열 길이에 묶인다.** 8자리로 적으면 10 m 단위로 값이 잘린다. 로컬 평면의
  미터 값을 MGRS로 저장했다 되돌리면 원값이 돌아오지 않는다.
- **격자 경계에서 산술이 깨진다.** 100 km 사각 문자가 바뀌는 지점을 지나는 이동 구간을
  선형보간하려면 결국 숫자 좌표로 되돌려야 한다. 보간 대상이 문자열이면 안 된다.
- 반대로 **위경도에서 MGRS로 가는 방향은 무손실이다.** datum이 같기 때문이다.

그래서 결론은 `geo.georef.mgrs = { store: false, display: true }` 다. 화면 라벨과
구두 보고 형식에는 MGRS를 쓰고, 저장은 하지 않는다. 이 AO는 전 구간이 **UTM zone 10,
위도대 F** 에 들어가므로 GZD는 `52S` 상수다(zone = floor((lon+180)/6)+1 = 10, 위도대 F는
남위 56도~48도). 100 km 사각 문자는 변환 라이브러리가 계산하도록 두고 여기에 적지 않는다.

> 출처 검증 상태: STANAG 번호와 정밀도 표는 2차 출처에서 왔고 **원문 대조 미완료**다
> (`02-research-plan.md` 출처 검증 체크리스트). 다만 위 설계 판단은 "MGRS가 WGS84
> datum 기반이고 자릿수가 정밀도"라는 성질에만 의존하며, 이는 변환 라이브러리 동작으로
> 직접 확인 가능하다.

## 3. 시간축 위의 위치

정지 자산은 고정 좌표, 기동 자산은 구간마다 좌표를 갖는다. ADR-0017의 반열린구간
`[from, to)` 표기를 그대로 쓴다.

### 3.1 정지 자산

```json
"geo": {"kind": "fixed", "frame": "TACGRID-01", "source": "asset-register",
        "accuracy_m": 15, "at": {"x": 10400, "y": 10900, "z": 418}}
```

### 3.2 기동 자산

```json
"geo": {"kind": "track", "frame": "TACGRID-01", "source": "asset-register",
        "accuracy_m": 25, "segments": [
  {"from": 0,   "to": 95,  "mode": "hold", "at": {"x": 8622, "y": 8192, "z": 146}},
  {"from": 95,  "to": 125, "mode": "move", "at":    {"x": 8622,  "y": 8192,  "z": 146},
                                           "to_at": {"x": 13842, "y": 12432, "z": 205}},
  {"from": 125, "to": 420, "mode": "hold", "at": {"x": 13842, "y": 12432, "z": 205}}
]}
```

### 3.3 시점 t의 좌표를 뽑는 규칙 (결정론)

`geo.position_rule` 에 같은 내용이 데이터로 들어 있다. 어떤 구현이든 이 규칙만 따르면
같은 값이 나와야 한다.

1. `kind == "fixed"` 이면 언제나 `at`.
2. `kind == "track"` 이면 `from <= t < to` 인 구간을 찾는다. 구간은 서로 겹치지 않고
   `[0, timeline.horizon)` 을 빈틈없이 덮는다.
3. `mode == "hold"` 이면 구간 내내 `at`.
4. `mode == "move"` 이면 `u = (t - from) / (to - from)` 으로 `at` 과 `to_at` 을 성분별
   선형보간한다. x, y, z 전부 같은 `u` 를 쓴다.
5. 어떤 구간에도 들어가지 않으면 위치는 0도 아니고 마지막 값도 아닌 **미정의**다.
   화면에 "위치 미상"으로 적는다.

5번은 ADR-0017이 "활성 단계가 없으면 저하도는 0이 아니라 미정의"라고 정한 것과 같은
태도다. 마지막으로 알려진 위치를 그대로 찍어두는 상황도는 **없어진 부대를 살아 있는
것처럼 그린다.**

**계산 예시** - `BN-CP`, `t = 110`:

```
구간 [95, 125) 의 move
u = (110 - 95) / (125 - 95) = 0.5
x = 8622 + 0.5 * (13842 - 8622) = 11232
y = 8192 + 0.5 * (12432 -  8192) = 10312
z =  146 + 0.5 * (  205 -   146) = 175.5
-> WGS84 lat -48.957366, lon -123.446051
```

### 3.4 왜 구간 표기이고 waypoint 목록이 아닌가

두 형태가 다 가능하지만 구간 표기를 골랐다.

- **구간이 자기완결적이다.** 각 구간이 시작점과 끝점을 다 갖고 있어 이웃 구간을 보지
  않고도 그 구간의 위치를 계산할 수 있다. waypoint 목록은 "다음 점"을 봐야 한다.
- **ADR-0017의 `outages`, `Phase.window` 와 같은 모양이다.** 시나리오 저작자가 시간
  표기를 두 종류 기억할 필요가 없다.
- **구간 표기 자체가 설명이다.** `note` 를 구간에 붙일 수 있고, "95~125분에 왜 움직였나"가
  데이터에 그대로 남는다. ADR-0017이 스냅샷 복제를 기각한 이유와 같다.

대가는 인접 구간의 끝점과 시작점이 같아야 한다는 중복이다. 이것은 검사로 잡는다(7절).

### 3.5 geo 와 outages 는 직교한다

**자산이 outage 중이어도 위치는 계속 정의된다.** 미전개 장비도 어딘가에는 있다.
`FO-TAB` 은 0~120분 `mobility` outage 중이지만 후방 집결지 `(3460, 4720)` 에 있고,
지도에 찍힌다. 통신이 안 되는 것과 존재하지 않는 것은 다르다.

반대 방향도 성립하지 않는다. **좌표가 움직인다고 outage 가 자동으로 생기지 않는다.**
`geo` 는 `outages` 를 만들지 않고 `outages` 도 `geo` 를 만들지 않는다. 저작 시 수작업으로
정합을 맞췄을 뿐이다.

tacnet-01에서 맞춰둔 정합은 다음과 같다.

| 구간 | outage | geo |
|---|---|---|
| 95~125 | `BN-SRV`/`BN-CP`/`SAT-TERM` mobility | 같은 구간에 `move` (1차 -> 2차 지휘소) |
| 150~195 | `L-VHF-CO1` terrain (능선 차폐) | `CO1-VEH` 가 `TF-RIDGE-A` 북사면 저지대 통과 |
| 205~235 | `L-VHF-CO2` mobility (안테나 미전개) | `CO2-VEH` 가 같은 구간에 `move` |
| 255~275 | `L-VHF-FO` terrain (계곡 진입) | `FO-TAB` 이 `TF-VALLEY-B` 로 하강 (z 214 -> 68) |

이 표가 지리 레이어의 실질적 용도다. 지휘관이 "왜 1중대가 끊겼나"를 물었을 때 상황도가
**지도 위에서** 능선 뒤로 넘어간 차량을 가리킬 수 있다. ADR-0012 2항이 요구한
"언덕을 적의 소행으로 보고하지 않기"의 시각적 대응물이다.

**단, 이것은 서술이지 계산이 아니다.** 아래 6절 참조.

## 4. 가상 좌표 안전성 - 어떻게 확보했는가

**요구: 실제 부대 위치도 실제 지명도 쓰지 않는다. 실제 군사시설과 우연히라도 겹치지 않는다.**

네 겹으로 막았다.

1. **앵커는 한반도 내륙의 일반 산악지대다.** `lat 36.45, lon 128.5` 를 임의로 골랐다.
   실제 부대 배치나 실제 시설 위치에서 유도하지 않았고 어떤 실제 편성도 참조하지 않았다.
   좌표를 한국에 둔 것은 지형 감각을 맞추기 위한 것이지 특정 지역을 지목하는 것이 아니다.
   AO 를 다른 산악지대로 옮겨도 시나리오는 그대로 성립한다.

   > **초안은 남태평양 공해였다.** 실제 시설과의 중첩 가능성을 원천 차단하는 선택이었지만,
   > 데모에서 지도 뷰가 빈 바다 위 격자가 되어 지형 감각을 전혀 주지 못했다. 지형 감각과
   > 안전성을 맞바꾸는 대신, 좌표를 내륙으로 옮기고 안전성은 **데이터의 성격**으로 확보한다.
   > 이 데이터에는 실제 시설에 대한 정보가 담겨 있지 않다. 담길 수가 없다. 전부 창작이다.
2. **영해·EEZ 밖이다.** EEZ 상한이 200 해리(약 370 km)인데 최근접 육지가 그보다 한
   자릿수 멀다. 어느 국가의 관할 수역도 아니다. 이 논거는 최근접 육지 수치가 반으로
   줄어도 성립한다.
3. **실제 지명을 쓰지 않았다.** `site` 라벨("여단 TOC", "능선 중계소", "포병 FDC",
   "1중대 지휘차")은 전부 일반명사다. `units` 도 "여단 / 1대대 / 1중대 / 포병중대"로
   편성 일반명이다. 지형 지물 이름("북쪽 능선", "동쪽 계곡")도 방위 일반명이다.
   앵커 해역의 고유명은 이 문서의 안전성 논거로만 언급하고 시나리오 데이터에는 넣지 않았다.
4. **지형은 로컬 평면 안에만 존재한다.** `geo.terrain` 의 능선·계곡·집결지는 창작물이고,
   앵커 지점의 실제 해저지형과 아무 관계가 없다.

이 논거들은 `mission.json` 의 `geo.safety` 블록에 데이터로도 들어 있다. 문서만 읽는
사람과 데이터만 읽는 도구가 같은 것을 보게 하기 위해서다.

### 4.1 배경지도 정책 - 이것을 어기면 3의 안전성이 무너진다

**`geo.safety.basemap_policy`: 위성영상이나 실지형 타일을 이 좌표에 깔고 "이 지형이
시나리오 지형"이라고 표시하지 않는다.** 지도 레이어는 빈 배경 + 격자 + `geo.terrain` 의
도식만 그린다.

이유는 명백하다. 앵커가 바다이므로 실제 타일을 깔면 파란 화면 위에 능선 중계소가 떠 있게
된다. 그 어긋남을 감추려고 앵커를 육지로 옮기는 순간 1~3의 안전성이 전부 무너진다.
**"지도가 그럴듯해 보이게" 하려는 압력이 안전성을 깎는 유일한 경로이고, 그 압력을 여기서
차단한다.**

바꿔 말하면 이 레이어의 배경은 지도가 아니라 **요도**다. 그 대신 격자·투영·심볼 배치·
MGRS 변환 같은 지도 배관은 전부 진짜 좌표로 검증된다.

## 5. `Asset.geo` 는 IP 지오로케이션이 아니다

혼동하면 ADR-0002 위반이다. 두 값은 이름만 비슷하고 성질이 정반대다.

| | `Asset.geo` (이 문서) | `enrichment.geo.country` (ADR-0002) |
|---|---|---|
| 붙는 곳 | **자산** (mission.json) | **이벤트** (OCSF 정규화 결과) |
| 출처 | 자산대장 / 기동계획. `source: "asset-register"` | 외부 IP 지오로케이션 DB |
| 신뢰도 | 신뢰 가능. 우리가 배치한 장비다 | 도시 수준 정확도 상한 약 75%. 클라우드 리전 편향 |
| 정밀도 | 미터 (`accuracy_m`) | **국가 코드까지만.** 도시 수준 표시 금지 |
| 판단에 쓰는가 | **아니다** (보조 표시 전용, ADR-0001) | **아니다** (참고값 전용, ADR-0002) |
| 왜 안 쓰는가 | 임무 저하도는 그래프가 낸다 | 값이 체계적으로 틀린다 |

**둘을 같은 필드에 넣지 않는다.** 스키마상으로도 물리적으로 분리되어 있다 -
전자는 `scenarios/*/mission.json`, 후자는 텔레메트리 정규화 산출물에 있고 이 저장소의
임무 그래프에는 존재하지 않는다. `mission.json` 의 `geo._not_ip_geolocation` 필드가
이 구분을 데이터에 박아뒀다.

재미있는 대칭이 하나 있다. 둘 다 판단에 쓰이지 않지만 **이유가 정반대다.** IP
지오로케이션은 틀려서 안 쓰고, 자산 위치는 맞지만 그것이 임무 중요도를 말해주지 않아서
안 쓴다. 상황도가 지리를 다루는 방식을 이 한 줄이 요약한다.

## 6. 한계 - 지금 없는 것

- **가시선·차폐를 좌표에서 계산하지 않는다.** `z` 값이 있고 능선 표고가 있지만 LOS
  계산기는 없다. `terrain` 원인 라벨은 **저작된 값**이고 좌표는 그것과 수작업으로 맞춘
  그림이다. 좌표에서 outage 를 유도하는 경로를 만들면 ADR-0017 3항이 원인 라벨을 저작
  입력으로 못박은 취지를 깎게 된다 - 기하가 원인을 만들기 시작하면 "지형인가 재밍인가"를
  구분할 수 없어진다.
- **정합성 검사기가 없다.** 3.5절 표의 대응은 지금 사람이 맞췄고 자동으로 검사되지
  않는다. `terrain` outage 구간에 해당 자산이 실제로 저지대에 있는지 확인하는 경고성
  검사는 만들 수 있다. 다만 **경고까지다.** 오류로 잡으면 위 항목과 같은 결합이 생긴다.
- **속도·기동 가능성을 검사하지 않는다.** 현재 값은 2.3~13.5 km/h 범위라 지상 기동으로
  타당하지만, 검증기가 상한을 보지는 않는다.
- **링크 기하가 없다.** 링크는 두 자산을 잇는 선으로 그릴 수 있지만 중계 반경, 안테나
  방향, 통달거리 같은 것이 없다. `03-mission-ontology.md` 8절이 이미 적은 "링크 용량·
  지연 없음"과 같은 계열의 공백이다.
- **로컬 평면이 회전을 지원하지만 쓰지 않는다.** `georef.rotation_deg = 0` 고정이다.
- **`z` 는 표고(MSL)이지 지면고가 아니다.** 항공 자산이 생기면 둘을 구분해야 한다.
  현재 시나리오에 항공 자산은 없다.
- **좌표 자체가 합성이다.** `07-synthetic-data.md` 6절의 원칙이 여기에도 적용된다 -
  이 좌표로 어떤 성능도 주장하지 않는다. 지리 레이어는 표시와 서술의 도구다.
