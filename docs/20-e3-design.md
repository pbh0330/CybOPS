불가능하다.** 지표를 못 재는 것과 나쁘게 나오는 것은 다른 문제다.

## 2. 골든셋을 손으로 수백 건 쓰지 않는다

계획서 9절이 최대 위험으로 "수작업 부담" 을 적었다. 골든셋 수백 건을 손으로 쓰면 그
위험이 그대로 현실이 된다.

**그럴 필요가 없다.** ADR-0003 이 LLM 의 역할을 이미 좁혀놨기 때문이다.

> LLM 은 요약, 설명, 상관 가설 생성, 자연어 질의, ATT&CK 매핑 서술만 담당한다.
> **LLM 출력이 상태값을 직접 결정하는 경로를 만들지 않는다.**

즉 브리핑의 사실 부분은 **결정론 엔진이 이미 계산해 놓은 것**이다. "t+300 에서 지휘통제
저하도가 얼마이고 공격·환경·상호작용 기여가 각각 얼마인가" 의 정답은 의견이 아니라
`Invoke-MissionPropagation.ps1` 의 출력이다. 단절된 링크와 그 원인 라벨, 침해 자산 목록,
격리 비용도 마찬가지다.

**그래서 요약 과제의 골든 정답은 리플레이에서 기계적으로 유도한다.** 시나리오 2종 x 28
스텝 x 질문 유형 여러 개면 수백 건이 손 안 대고 나온다.

이것이 값싼 우회가 아니라 **이 설계가 애초에 그렇게 되어 있어서 가능한 것**이라는 점이
중요하다. LLM 이 상태를 정하는 구조였다면 정답이 없어 손으로 써야 했을 것이다.

### 자동 유도로 만들 수 없는 것

| 과제 | 정답 출처 | 자동 유도 |
|---|---|---|
| 상황 요약 | 엔진 출력 | **가능** |
| 원인 분해 서술 | 엔진 출력 | **가능** |
| 봉쇄 비용 서술 | 엔진 what-if | **가능** |
| 자연어 질의 | 엔진 상태 조회 | **가능** |
| 상관 가설 | 저작된 공격 타임라인 | 부분 - 시나리오는 가능, 실데이터는 불가 |
| ATT&CK 매핑 | OpTC 라벨 101건 | 부분 - `attack_candidates` 는 **키워드 휴리스틱**이라 검토 필요하다고 라벨 파일이 스스로 적어뒀다 |
| 프롬프트 인젝션 | 저작 | 이미 있음 |

ATT&CK 매핑은 그대로 정답으로 쓰지 않는다. 라벨 파일의 경고를 무시하고 휴리스틱 매칭을
그라운드트루스로 승격시키면, 측정하는 것이 모델의 매핑 능력이 아니라 **우리 키워드 목록과
모델의 일치도**가 된다.

## 3. 확신도를 어떻게 받을 것인가

캘리브레이션을 재려면 모델이 문장마다 확신도를 말해야 한다. 그런데 **확신도를 요구하는
방식이 결과를 만든다.**

- "확신도를 0-100 으로 적어라" -> 대부분 90, 95 로 몰린다. 자유 서술 숫자는 캘리브레이션이
  아니라 화법을 측정한다.
- **선택지 방식** -> 문장마다 `certain / likely / unsure` 중 하나를 고르게 하고, 각 구간의
  실제 정확도를 잰다. 구간이 셋뿐이라 ECE 가 거칠지만 **비교 가능**하고, 모델이 흉내낼
  여지가 적다.

셋으로 간다. 그리고 **거부(abstention)를 1등급 시민으로 둔다** - 근거가 없으면 "모름" 을
고를 수 있어야 하고, `04-evaluation.md` 가 거부율을 지표로 적어둔 이유가 그것이다.
거부가 불가능한 설문은 확신도를 위로 밀어올린다.

## 4. 무엇을 측정하지 않는가

- **요약이 유용한가는 측정하지 않는다.** 자동 유도한 골든셋은 "사실을 맞게 적었는가" 만
  묻는다. 지휘관이 읽고 판단에 도움이 되었는가는 다른 질문이고, ADR-0015 로 전문가 평가를
  하지 않기로 했으므로 이 과제에서는 **측정하지 않는다고 적는다.** 못 재는 것을 잰 척하지
  않는다.
- **일반화.** 시나리오 2종, 모델 3~4종.
- **파인튜닝 비교 없음.** ADR-0006, 계획서 원칙 6.

## 5. 첫 실측 (2026-09-08)

프롬프트 v3, `qwen2.5:7b-instruct-q4_K_M`, tacnet-01 의 t+120 / t+300 / t+390 세 시점.

```
인용 검사 (Test-BriefingCitations)
  인용률 100% (기준 80%), 위반 0건, 세 시점 전부 PASS

골든셋 채점 (Test-GoldenBriefing)
  문장 9, 태그 9, 무태그 0
  정답 5 / 오답 1 / 거부 0

  등급      주장    n   정답  오답   실제정확도
  확신      95%     8    5     1     83.3%
  추정      70%     1    -     -     -
  근거없음   0%     0    -     -     -

  ECE   0.1167     Brier 0.1525
```

표본이 9문장이라 **이 수치로 모델을 평가하지 않는다.** 지금 확인된 것은 파이프라인이
끝까지 돈다는 것과, `확신` 이라고 말한 문장의 실제 정확도가 83.3% 로 **주장(95%)보다
낮다**는 방향뿐이다. 과신 방향이고, 모델 비교의 대상이 될 양은 아니다.

`추정` 이 1건, `근거없음` 이 0건인 것이 더 큰 문제다. 등급이 셋인데 하나만 쓰이면
캘리브레이션 곡선이 점 하나가 된다. 근거 팩이 20~26 사실로 충분해서 모델이 모른다고
말할 일이 없었기 때문인데, **일부러 사실을 뺀 팩**을 만들어야 거부와 `추정` 이 나온다.
6절 작업 순서에 넣었다.

### 여기까지 오면서 잡은 것

**인용 검사가 확신도 도입의 회귀를 잡았다.** v2 는 인용(규칙 2)과 확신도(규칙 10)를 따로
두었고 모델은 마지막 문장에만 둘 다 붙였다. 인용률이 66.7% 로 떨어져 위반이 났다.
검사가 없었다면 **캘리브레이션 지표를 얻은 대가로 ADR-0009 를 조용히 깨뜨렸을 것이다.**
v3 에서 두 요구를 문장 종결 형식 하나로 합쳐 부분 준수가 형식 위반이 되게 했다.

**채점기 자체가 두 번 틀렸다.** 둘 다 "그럴듯한 숫자" 를 냈다는 점이 같다.

1. 골든셋은 `100.0%`, 모델은 `100%` 로 쓰는데 문자열로 비교해 **전 문장 오답**이 나왔다.
   숫자로 비교하도록 고쳤다.
2. `$BAND`(해시)가 `$band`(문자열)에 덮여 주장 확신도가 전부 0 이 됐고, ECE 가 0.8333
   으로 나왔다. 정확도 83% 인 모델에 대해 계산된 값이다.
   **틀린 캘리브레이션 지표는 없는 것보다 나쁘다** - 완벽해 보이거나 최악으로 보이거나,
   어느 쪽이든 읽는 사람이 그것을 믿는다.

2번은 이 저장소에서 **세 번째 같은 버그**다(`$T`/`$t`, `$l`/`$L`, `$BAND`/`$band`).
PowerShell 변수가 대소문자를 구분하지 않는다는 것을 알고 있었는데도 세 번 밟았다.
대문자로 쓰는 것은 방어가 아니다. **이름이 대소문자로만 다르면 같은 변수다.**
